## 4. 逐项结论与证据

### 4.1 S1 · SH 降 DC（M1）— ✅ 零误差

- 数学恒等式：`eval_sh` 线性，c[3..47]=0 ⇒ `rgb ≡ max(0, 0.5+DC·SH_C0)`。
- 上传侧：检测 `sh_degree`（资源元数据优先，回退扫描 f_rest 字节带），DC-only 时 SH 纹理 1 texel/splat（RGBA16F）。
- 着色器：`sh_degree==0` 走 1 次 texelFetch + 3 次 MAC，跳过 12 texel + eval_sh（60 MAC）。
- 实测：fleet 两机位 **PSNR=100.00 / SSIM=1.0000 / maxΔ=0**；VRAM 87→57MB（fleet）、159→91MB（whale）。
- A/B 开关：`gdgs/opt/sh_dc_force`（-1 自动 / 3 强制全阶，用于复现基线布局）。

### 4.2 A2 · inverse 预计算（M1）— ✅ 逐位等价（fleet）

- 后端每实例每帧（transform 变化时）CPU 算 `inverse(node.global_transform.basis)`，uniform 传入；着色器删每 splat 的 `inverse()`。
- 与 S1 叠加后 view_dir 在 DC 路径根本不再计算（零额外成本）。
- 开关：`gdgs/opt/inv_precompute`。

### 4.3 A4 · ext 预计算（M1）— ✅ 零像素误差

- 上传时把 `min(quad_extent, sqrt(2·ln(op/cutoff)))` 写入 core t2.w（原 pad）。
- 正确性论证：baked ext 用静态 opacity（不含 breathe）；波浪 breathe≤1 只会使实际所需 ext **更小**，
  baked ext 是**上界** → 片元 discard 依旧裁出完全相同的区域（像素不变，仅极少量过绘制）。fleet（breathe=1）逐位等价。
- 开关：`gdgs/opt/ext_precompute`。

### 4.4 M2 · 片元 SFU（B1/B2）— ⚠️ 本卡无收益

- **B1**（`exp→exp2(p·LOG2E)`）：GLSL 编译器在 NVIDIA 上本就把 `exp()` 降为 `exp2()`，改动是恒等变换 → **实测中性**（预期内）。
- **B2**（sRGB 3×pow(2.4) → 256 项 1D LUT，3 次硬件滤波取数）：
  - 分支版实测 whale **+2.3%/+2.6%**（变慢）；无条件 LUT 仍比 M1 单独慢 ~3pp → **纹理取数比 SFU pow 更贵**。
  - 结论：方案假设"片元 SFU 洪峰"在 RTX 5060 上不成立（SFU 流水线与纹理带宽相比并非瓶颈）；**B2 默认关闭**，
    保留 `gdgs/opt/srgb_lut` 开关供其它 GPU 复测。
  - 像素：开启时 maxΔ=1（PSNR 96–98dB），符合 <2/255 误差上界。

### 4.5 M4 · C2 min_pixel_size — ⚠️ 默认关闭（破坏性）

- 实现：后端从 `gdgs/opt/min_pixel_size` 设置 uniform（着色器已有剔除逻辑，未改）。
- **发现**：fleet/whale 评测场景在相机距离下 splat 大量亚像素 —— N=1.0 时 fleet 两机位截图**全空**（non-bg 0.0%），
  N=0.5 wide 全空、N=0.3 wide 剩 0.3%（原始 1.0%）；PSNR 23–29dB / maxΔ≈250，远超验收线。
- 结论：该场景"远处 shimmer"就是画面内容本身，C2 会连同真实内容一起剔掉。**默认 0（关）**，保留为
  面向"真·亚像素噪点"场景的质量/性能滑杆（方案原意）。

### 4.6 M3 · 顶点 SFU（A5/B4）— ✅ 已实现（直接编辑，装饰性）

- A5：`fract(sin())` → 整数哈希（每顶点省 2 个 sin）。
- B4：`pow(zf,1.6)` → `zf·sqrt(zf)`（≈zf^1.5，省 1 SFU）；`pow(x,2)` → `x·x`（精确恒等，纯 ALU）。
- 无误差约束（装饰性扰动）；仅 whale 波浪路径执行。交错电池中贡献约 2pp mean（w3 全开 -7.2% vs M1 单独 -5.3%）。
- 未做 uniform 开关（运行时分支会迫使编译器保留两条路径、吃掉收益）；A/B 采用"文件级快照"对比。

## 8. C1 与 M5 执行记录（本轮，含一次结论更正）

### 8.0 一句话总结

C1 做完了但**不值得开**（正确、像素零误差，但 GDScript 开销抵消了收益）；E2/A1 经测量判定**必须走 GPU**（CPU 在 GDScript 下不可行），而这两件事恰好是 Compute 后端**本来就成立**的结构（每 splat 只算一次）；D 的 4.7 阻塞**已定位并修复**，共修 7 个 bug，**Compute 现已渲染正确并在 whale 上快 2.4 倍**（3.047ms -> 1.247ms，交错电池 min-of-6 + 96% 画面覆盖证据）；但 fleet（多实例小编队）上慢 36%，故**默认后端仍为 Raster**，Compute 作为"单云奇观场景"的选项。此前报告里那个 3x 数字作废，修复后重测的 2.4 倍有效。

### 8.1 C1 · 距离感知排序 —— 已实现，结论：默认关

实现（开关 gdgs/opt/far_sort_fraction，0 = 关）：
- raster_sorter.gd::sort_into_aware：远/近集合的阈值取**上一帧第 K 远那个 splat 在当前帧的 key**（K = n x fraction，自适应，不会冻结）；远块按上一帧相对顺序原样保留，近块用紧凑 near_list 做计数排序后接在其后，整体仍是 back-to-front。
- raster_sort_job.gd：把 front buffer 作为 prev_order 交接给 worker；force_full 参数（首帧 / 相机突跳 >10 度）退化为完整排序，避免远块冻结旧顺序。
- raster_render_backend.gd：FULL_RESORT_DOT_THRESHOLD（约 10 度）决定是否 force_full。
- 顺带一个通用收益项：计数排序的 bucket 只算一次（原先 histogram + scatter 各算一次 int()），whale 408k 完整排序 **55.8ms -> 50.4ms（-10%）**，此项无条件生效。

实测（RTX 5060 / 720p / vsync off）：

| 项目 | 结果 |
|---|---|
| fleet 像素 A/B（far_sort_fraction=0.8 vs 0） | **PSNR=100.00 / SSIM=1.0000 / maxDelta=0**（wide+close 两机位） |
| fleet 交错电池（min-of-4 runs，warmup=90/frames=180） | base 0.886ms -> 出厂默认 0.860ms -> **c1 0.839ms**（mean）；p95 1.006 -> 1.002 -> 0.971 |
| whale 排序 worker 耗时（408k） | 完整排序 55.3ms vs C1@0.8 **61.6ms（+11%）**，实得远块占比约 70% |

结论：C1 在**像素意义上完全正确**（shot 机位切换会触发 force_full，两机位逐位一致），但：
1. 排序在 worker 线程，**帧时间本来就不含它**，省不到帧时间；
2. GDScript 下多走一遍 prev_order 扫描 + near_list 的开销**大于**少排一遍直方图的收益，排序本身反而慢 11%；
3. 电池里 c1 比出厂默认好 2.5pp，但在约 4% 噪声底之内，不能算显著。

-> 计划里 408k 排序成本大降的预期在 GDScript 下不成立，**默认 0（关）**，保留开关供将来排序迁到 GPU/C# 时复用。

### 8.2 A1 · compute 预投影 —— 判定：Compute 后端已结构性满足，Raster 侧不建议做

- Compute 后端的 gsplat_projection.glsl 本来就是**每 splat 一个 invocation**：投影、特征值、SH、relight、波浪全部只算一次，再按 tile 复制。也就是说每 splat 算 1 次、4 角复用，在 Compute 路径**已经是现状**。
- Raster 侧要做同等事，必须在 Raster 后端（目前完全不用 RenderingDevice）里新建 RD compute pass + 渲染线程同步 + Texture2DRD 绑定；CPU 预投影则不可行：408k x 约 60 flops/帧在 GDScript 下是几百 ms 量级。
- 建议：**把 A1 的目标交给 Compute 后端**（见 8.4 剩余问题），Raster 侧维持现状。

### 8.3 E2 · 波浪时间网格采样 —— 判定：CPU 不可行，须 GPU

实测 GDScript sin() 吞吐：200 万次 = 94ms -> **47ns/次**。
计划要求 15Hz（66ms 预算）x 408k splat x 2 采样 x 4 个 sin，约 **153ms/次**，超预算 2.3 倍；即使降到 7.5Hz 也只有 1 采样能勉强塞进预算，误差会超过计划的 2% 上界。

更关键的是：Compute 后端的投影 pass **每 splat 只求值一次波浪**（比 15Hz 网格更准：零时间采样误差、无需双缓冲防撕裂）。所以 E2 的正确落点是 GPU（compute pass），而不是 CPU worker + 双缓冲纹理。

### 8.4 D · Compute 后端启用 —— 4.7 阻塞已解决 + 6 个 bug 已修，但仍不渲染

#### 找到并修复了 research/06 踩坑4 的根因（本轮最有价值的产出）

**Godot 4.7 的 Compositor.compositor_effects getter 返回副本，append() 静默无效**：

    comp.compositor_effects.append(fx)   # 静默失效：append 后 size() 仍是 0，效果从未挂上，因此无输出

实测：append 后 size() 仍为 0；改成 copy-append-assign 后立刻变 1，回调开始触发（callback type=3）。
修法：GaussianCompositorEffect.make_compositor_with(effect) + 新增 ensure_in_tree(node)（单例、幂等；后端自己拥有合成器，bench_runner.gd / main.gd 均改为调用它）。

#### 另外修复的 6 个 bug（都在 Compute 路径上，逐个是修完才暴露下一个）

| # | 文件 | 问题 | 影响 |
|---|---|---|---|
| 1 | gaussian_scene_registry.gd:311 | var enabled := amp != 0.0 and axis.length_squared() > 0.0 由 Variant 推导失败 | **Compute 后端整个脚本编译不过**（所以历史上从没真正跑起来过） |
| 2 | gaussian_gpu_state_cache.gd / gaussian_renderer.gd | 投影 shader 的 Uniforms（binding 8）是 std140：vec3 占 16 字节 -> 块大小 48；CPU 只给 36 字节且紧密排列 | shader 按源码重编译后（清缓存 / --import）投影 pass 直接失效（此前能跑是因为用了 **M1 之前的旧 SPIR-V 缓存**） |
| 3 | gsplat_projection.glsl | splat_time = time - splat.time，而所有 PLY 的 time=0 -> 前 0.35s time_factor_late=0 -> **opacity=0**；Raster 根本不看 time | 开跑前 0.35s 整场不可见（短测直接拍空图） |
| 4 | gsplat_projection.glsl | 每 splat 的 sort 预算 MAX_SORT_ELEMENTS_PER_SPLAT=10，但参考实现那句 num_tiles_touched > grid/3 护栏被注释掉了 | 巨型 splat 写爆 sort_keys/sort_values -> 整条 radix 结果被污染（实测帧时间 **197ms**、输出为空） |
| 5 | gaussian_renderer.gd | 每帧只 clear 直方图前 4 + 4*RADIX*4 字节，partition 直方图区残留 | radix 排序第 2 帧起产出乱序 key |
| 6 | bench_runner.gd | whale 截图机位绕**原点**（_tick_orbit 是绕鲸鱼当前位置） | whale 截图永远拍空 |

（另外：rd.barrier() 在 4.7 已废弃——Barriers are automatically inserted by RenderingDevice，不要手动加，加了会刷 5783 条警告。）

#### 最后一根稻草：Uniform block 是紧凑成员偏移，不是 std140（已修复）

回读 GPU buffer 拿到决定性证据：culled_buffer[*].image_pos.x 是 **5.3e8**（屏幕坐标应 0~1280），而 image_pos.y、pos_xy、view_depth=62.16、color.a=0.883 全部正常。因为 y 正常，一开始误判为巨 splat（我加的 tile clamp 恰好把垃圾 X 掩盖成大 rect）。

让 shader 自己把 uniform 读到的值写进输出（临时探针，已移除），一次定位：

    shader_dim_x = 1067852992   <- 这是 float 1.3 的位模式 = time 的值
    shader_dim_y = 1280         <- CPU 写的 dims.x
    shader_point_count = 720    <- CPU 写的 dims.y

即投影 shader 的 Uniforms（binding 8）**成员偏移是紧凑的**：camera_pos 占 0-11、time 12-15、dims 16-23、point_count 24、light_count 28、sh_degree 32（**没有 std140 的 vec3 16 字节对齐**），而块总大小仍然向上取整到 **48 字节**——正是"成员紧凑 + 总大小 48"这个组合，让最初那条 size (36) smaller than shader uniform (48) 的报错把我引向了错误的 std140 修法。

正确写法：**9 个紧凑 float + 3 个尾部 padding float = 48 字节**（create_uniform_buffer(12*4) 保持不变，内容改回紧凑排列）。修完 image_pos 恢复为 [640.1, 355.4]（1280x720 画面中心），渲染立刻正常。

#### 修复后实测（whale 408k，交错电池 min-of-6）

| 配置 | mean | p95 | p99 | VRAM |
|---|---|---|---|---|
| base（全部优化关，Raster） | 3.272ms | 3.920ms | 4.084ms | 159MB |
| Raster（出厂默认） | 3.047ms | 3.701ms | 3.794ms | 91MB |
| **Compute** | **1.247ms** | **1.720ms** | **2.021ms** | 464MB |

-> Compute 比出厂默认 **mean -59%（约 2.4 倍快）、p95 -54%**，且这次**渲染正确性已证据化**：鲸鱼 shot 覆盖 885,059 / 921,600 像素（96% 画面）。

#### 但 fleet（100 个实例的小编队）上 Compute 更慢 —— 默认后端仍保持 Raster

| 场景 | Raster（出厂默认） | Compute | 结论 |
|---|---|---|---|
| whale 408k（单节点大云） | 3.047ms | **1.247ms** | Compute 快 2.4 倍 |
| fleet 225k（100 节点小编队） | 0.897ms | 1.452ms | Compute **慢 36%** |

原因：Compute 每帧固定开销（投影 dispatch + 4 遍 GPU radix + 3600 个 tile 工作组）在"多实例 + 亚像素 splat"的 fleet 上摊不开；而 whale 这种"一个巨大云 + 大量过绘制"正是 tile 遍历的强项。VRAM 也是 464MB vs 91MB（约 5 倍）。

跨后端像素一致性（fleet 同机位）：PSNR 31.9-35.0dB / **SSIM 0.9926-0.9947** / maxDelta 223-251 —— 结构一致，差异来自两个后端**固有的混合空间不同**（Raster 逐 splat 在 sRGB 空间走硬件透明通道，Compute 在计算纹理里累积后再合成），插件源码本身注明这是 inherent 差异。

因此本轮默认后端**仍为 Raster**，使用建议：**whale / 太阳系巨物这类单云奇观场景把 gdgs/rendering/backend 设为 Compute（2.4 倍）**；fleet 这类多实例战斗场景保持 Raster。进阶做法是让 Auto 按"节点数少 + 点数多"自动选边（后端选择目前是启动期一次性的，可改成首次 attach_node 时按场景特征决定）。

#### 结论更正（重要）

第 1 章里那张 whale 3.147ms -> Compute 1.049ms（-200%）的电池数据仍然**作废**（那批运行用的是旧 SPIR-V 缓存，鲸鱼被渐显 bug 压到近乎透明，等于在测一张几乎空的画面）；但修复后重测的 **3.047ms -> 1.247ms（2.4 倍）是有效的**——这次有渲染正确性证据（96% 画面覆盖）+ 交错电池背书。

### 8.5 顺带踩到的一个坑（值得写进 CLAUDE.md）

project.godot 的注释符是**分号**，不是井号。用井号写注释会让解析在那一行中断，**整个 [gdgs] 段的设置全部丢失**（ProjectSettings.has_setting(gdgs/rendering/backend) == false），后端选择于是回落到 Auto -> 自动偏好 Compute——表象是明明设了 Raster，却在跑 Compute。
